# Data Catalog & Metadata Search Engine

**Category:** Data Analytics
**Difficulty:** X

**Status:** Implemented (Python)

Point it at SQLite files, DuckDB files and folders of Parquet, CSV and JSON. It discovers every
table and file, profiles each column, tags likely personal data, infers foreign keys that no
source declares (also across sources), and indexes everything in a single SQLite catalog. The
catalog has BM25 full-text search fused with trigram substring search. Re-crawls are incremental
and keep a schema change log. A CLI and a small FastAPI search page sit on top.

## Run it

```bash
uv run --locked pytest -q                         # 25 tests (the symlink test skips on Windows without privileges)
uv run catalog crawl ./warehouse.duckdb ./exports/ shop.sqlite
uv run catalog search "customer email"            # --tag pii, --mode fts|like|hybrid
uv run catalog show orders                        # columns, profile, relationships (--json)
uv run catalog relations                          # declared and inferred foreign keys
uv run catalog changes                            # schema change history
uv run catalog serve                              # search page at http://127.0.0.1:8000
uv run catalog demo                               # build the TPC-H demo estate, write results/
```

The catalog file defaults to `./catalog.sqlite` (`--catalog` to change it). The demo needs
DuckDB's `tpch` extension, which DuckDB downloads on first use; the generated data goes to
`data/` (gitignored).

## How it works

**Discovery and profiling** (`crawl.py`). A folder is walked, skipping hidden entries and unknown
extensions. SQLite is recognised by its 16-byte header, not just its extension. Every source is
opened read-only. SQLite metadata comes from `PRAGMA table_info` and `PRAGMA foreign_key_list`,
DuckDB's from `information_schema` and `duckdb_constraints()`, and files are described by DuckDB's
`read_parquet`, `read_csv` and `read_json`. One aggregate query per table gathers the row count
and, per column, nulls, distinct count, min and max; a second query samples up to 50 distinct
values. Every identifier and path that comes from a source is quoted, so a table named
`x"; DROP ...` is just a name.

**PII tagging** (`pii.py`). Name rules (email, phone, IP, person name, postal address, birth
date, national ID, payment card) and value rules (email, phone, IPv4, SSN shape, and card
numbers that pass the Luhn check). A value rule fires when 80% of the sample matches. Shapes that
collide are separated explicitly:

- an ISO date or a plain decimal looks like a phone number, so it is excluded;
- a phone number has at most 15 digits (E.164), which separates it from a card number;
- `ip_address` and `email_address` are not postal addresses.

**Foreign-key inference** (`relations.py`). A pair child.a -> parent.b is proposed only when
three things hold:

- parent.b is a key (unique, no NULLs);
- the names agree, either equal after dropping a short table prefix (`l_orderkey` ~
  `o_orderkey`) or the child is the parent table's singular plus `id`/`key` (`user_id` ~
  `users.id`);
- at least 99% of child.a's distinct values occur in parent.b.

Names alone over-match, since every table has an `id`. Values alone also over-match: any column
of small integers fits inside a 1..n surrogate key. Both are required. Declared keys are kept and
labelled `declared`.

**Search** (`store.py`). Each dataset and each column is a document in two SQLite FTS5 indexes:

- a word index with the Porter stemmer and BM25, weighted name 10 : tags 5 : context 2.
  Identifiers are split for it (`l_extendedPrice` -> `l extended price lextendedprice`);
- a trigram index over names, which matches substrings inside compound identifiers (`price` in
  `l_extendedprice`).

Hybrid mode merges the two rankings with reciprocal rank fusion (score = sum of 1 / (60 + rank)).
User text is reduced to alphanumeric terms and each is quoted before it reaches `MATCH`, so FTS5
query syntax cannot be injected.

**Incremental crawl** (`indexer.py`). A source whose size and mtime have not changed is skipped.
A changed source is re-profiled and diffed against its stored schema (added, dropped and retyped
columns go to `schema_changes`). Datasets that disappeared from a crawled folder are removed.
Relationships are re-inferred over the whole catalog after every crawl.

## Results

`uv run catalog demo` builds a demo estate. TPC-H at scale 0.01, generated by DuckDB, is split
three ways: `customer`, `orders` and `nation` go into SQLite, `lineitem`, `part`, `supplier` and
`partsupp` into a DuckDB file, and `region` into Parquet. Next to them sit a synthetic `users.csv`
(500 fake people) and `events.jsonl`. That makes 10 datasets in 4 source kinds, and none of them
declares a foreign key. The TPC-H specification's keys plus the two demo links (11 in all) are the
ground truth. `results/evaluation.md`:

| Check                            | Precision | Recall | Notes                                                                          |
| -------------------------------- | --------- | ------ | ------------------------------------------------------------------------------ |
| Foreign-key inference            | 1.0       | 1.0    | 11 of 11, e.g. `users.customer_id -> customer.c_custkey` across CSV and SQLite |
| PII tagging (9 true PII columns) | 1.0       | 1.0    | before the date/decimal/digit rules it was 0.82: prices were tagged as phones  |

Search over 16 labelled queries (mean reciprocal rank of the first relevant hit, and whether one
appears in the top 5):

| Mode                         | MRR   | Hit@5 |
| ---------------------------- | ----- | ----- |
| `LIKE` substring baseline    | 0.736 | 15/16 |
| FTS5 BM25 on words           | 0.669 | 13/16 |
| Hybrid (BM25 + trigram, RRF) | 0.906 | 15/16 |

Word search alone lost to plain `LIKE`. Warehouse column names are compounds (`o_orderpriority`,
`c_mktsegment`, `p_retailprice`) that no tokenizer splits into the words people type, so "order
priority" or "price" found nothing by word. Trigram matching recovers them, and fusing it with
BM25 keeps BM25's ordering when words do match. The one query every mode misses is "account
balance" against `c_acctbal`: an abbreviation is neither a word nor a substring match, and
catching it needs a synonym list or embeddings.

## Security

Crawled sources are untrusted input. A DuckDB file can contain a view such as
`SELECT * FROM read_csv('~/.ssh/id_rsa')`, and profiling that view would copy the file into the
catalog's sample values. DuckDB's `read_only` flag does not stop that, so crawled DuckDB files are
opened with `enable_external_access = false`. Such a view then fails with a permission error and
the crawl reports it. A test covers this. The finding came from a security review of this
challenge. The search page is read-only: it reads only the catalog, never a source or a
request-supplied path, and it renders every value with `textContent`.

A second review pass added three more guards:

- Symlinks found inside a crawled folder are skipped, so a link cannot pull an arbitrary file
  into the crawl.
- A column tagged as PII keeps its counts but not its sample values, min or max. The catalog
  records that the data is personal without copying it.
- The server answers only requests addressed to `localhost`, `127.0.0.1` or `[::1]` (plus the
  `--host` it binds and any names in `DATA_CATALOG_HOSTS`). Another web page therefore cannot
  read the catalog through DNS rebinding.

## Limits

- Composite keys are not inferred (TPC-H's `lineitem (l_partkey, l_suppkey) -> partsupp`).
- Inclusion is computed on full distinct sets up to 200,000 values per column; a large estate
  would need sketches (MinHash or Bloom filters) instead.
- Profiling scans each table fully for `count(DISTINCT)`; sampling would bound the cost.
- A DuckDB table whose name itself contains a dot is shown as `schema.table` and cannot be
  re-read for inference.

## Where this is actually used

This is the core loop of open-source metadata platforms. DataHub ingests metadata through
"recipes" that pair a source (Snowflake, for example) with a sink, and its documentation describes
pull-based integrations that crawl data systems on a schedule: databases, warehouses, BI tools,
orchestrators, S3 and Iceberg. Search over the collected names and descriptions is how people
then find a table without asking around.

The relationship side matches what dbt teams already assert by hand. dbt ships four generic data
tests, `unique`, `not_null`, `accepted_values` and `relationships`. Its documentation's example
checks that every `customer_id` in `orders` exists as an `id` in `customers`, which is the
inclusion test this crawler runs to propose keys nobody declared.

The search stack is stock SQLite. FTS5 provides a built-in `bm25()` ranking function, and its
trigram tokenizer extends FTS5 to substring matching in general. Both indexes here are ordinary
FTS5 tables in one file, with no search server to run.

## Files

- `src/data_catalog/crawl.py`: discovery, read-only connections, profiling, value sampling
- `src/data_catalog/pii.py`: name and value rules, Luhn check
- `src/data_catalog/relations.py`: foreign-key inference
- `src/data_catalog/store.py`: catalog schema, FTS5 indexing, search modes, schema diffs
- `src/data_catalog/indexer.py`: incremental crawl and relationship refresh
- `src/data_catalog/cli.py`, `server.py`, `static/index.html`: CLI, API and search page
- `src/data_catalog/demo.py`: demo estate builder and evaluation
- `results/evaluation.{md,json}`: the numbers above
